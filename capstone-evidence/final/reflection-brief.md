### System 1 — Agentic loop

1. **Loop control.** Quote the `stop_reason` sequence from one trace. Name the file and function that decides continue-vs-stop, and how.
→ The offline trace `system-1-agentic-loop/trace-claim_01_kitchen_fire.jsonl` records turns 1–5 as `stop_reason=tool_use` (tools: `lookup_policy`, `record_claim_fact`, `classify_claim`, `assess_severity`, `route_to_adjuster`) and turn 6 as `stop_reason=end_turn` with empty `tool_calls`. 2. **Anti-pattern.** Name one anti-pattern `test_antipatterns.py` checks for. What would break in your run if the loop used it?
→ `tests/test_antipatterns.py::test_no_integer_literal_iteration_cap_in_loop` statically rejects `for _ in range(<int literal>)` and `while <var> < <int literal>` in `loop.py`. If the loop used a literal cap (say 5) as its primary stop, the offline 6-turn claim (`offline-trace.txt`: 5 tool turns + final `end_turn`) would have been truncated mid-routing — `route_to_adjuster` at turn 5 would never execute and the claim would end `incomplete` instead of `routed`. The companion check `test_no_string_membership_against_text_in_loop` similarly forbids steering on magic strings in assistant text; control flow must come only from `stop_reason`, with the config-sourced `Budget` (`budget.py`) as the safety net.

3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?

The terminal pair `route_to_adjuster` / `escalate_to_human` is likewise disambiguated ("Call … when confidence is at least 0.6 and severity has been assessed" vs "when confidence is below 0.6 … or the claim cannot be routed safely"). When my demo first called `route_to_adjuster` with the wrong fields, the dispatcher returned a structured `{"is_error": true, "error_category": "permanent", "is_retryable": false, "message": "claim_summary must be a string"}`-shaped error (see `_t_route_to_adjuster` in `tools.py`) instead of raising into the loop — so the agent could read the machine-checkable `error_category`/retryability and correct the call on the next `tool_use` turn rather than crashing the run the way an exception or an opaque string would.

### System 3 — Claude Code config

8. **Path-scoped rules.** Quote the glob frontmatter from one rule file. Why is it better than a directory-level CLAUDE.md for cross-cutting conventions?
→ `.claude/rules/tests.md` (copied to `config/.claude/rules/tests.md`) declares `paths: ["**/*.test.tsx", "**/*.test.ts"]`, and `react.md` declares `["src/components/**/*", "src/pages/**/*"]` while `api.md` declares `["src/api/**/*"]`. The root `CLAUDE.md` scope table states the rationale verbatim: "We prefer `.claude/rules/` with glob `paths:` instead, so cross-cutting conventions (e.g. test files everywhere) work cleanly." A directory-level `CLAUDE.md` only fires for files beneath that directory, so co-located tests (`Foo.test.tsx` next to `Foo.tsx`, anywhere in the tree) could not be covered by one file; the glob rule fires wherever a test file is edited and layers on top of the react/api rules — proven by `test_ac_02_06_test_file_matches_react_and_tests` in `test-output.txt` (35 passed).

9. **Forked skill.** Quote the `context: fork` and `allowed-tools` lines. What does running forked + read-only buy you? What breaks without it?
→ `config/.claude/skills/deploy-check/SKILL.md` frontmatter: `context: fork`, and `allowed-tools: [Read, Grep, Glob, Bash(git status:*), Bash(git diff:*), Bash(git log:*), Bash(git rev-parse:*), Bash(git ls-files:*), Bash(gh pr view:*), Bash(gh pr checks:*)]` — no Edit/Write. Forked execution keeps the megabytes of discovery output (file enumeration, diff parsing, check traces) inside the sub-agent so only the structured `verdict: pass | fail` summary returns to the main session; the skill doc states this explicitly ("those stay in the fork"). Read-only tools guarantee the pre-deploy audit cannot itself mutate the tree it validates. Without fork, every deploy check would contaminate the main context with throwaway output; without the read-only allowlist, a misbehaving check could write files or push commits during what is supposed to be an inspection — the validator enforces both (`test_ac_04_02`, `test_ac_04_03` passed).

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
→ Warm tier holds 40 defects (`fixtures/defects.json`); the shift run with `--since 2026-04-01T00:00:00Z` returned a 17-row slice (`run-output.txt`: "shift C: 17 new defects"). The query is `WarmStore.defects_since` in `shift_monitor/warm.py`: `SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?`, served by index `idx_defects_ts` — `EXPLAIN QUERY PLAN` returned `SEARCH defects USING INDEX idx_defects_ts (ts>?)`. The model never sees the full history because `pipeline.gather_new_defects` is a pure passthrough to that query (asserted by `test_gather_new_defects_is_pure_passthrough_to_sql` and `test_gather_new_defects_has_no_python_side_filtering` in `test-output.txt`: 33 passed), and `build_rich_prompt` caps the prompt under 4000 chars — filtering happens in SQLite before anything enters context, so per-shift cost stays flat as history grows across shifts.

12. **Crash recovery.** The resume-vs-fresh decision and its staleness threshold (`recovery.py`). Why is a fresh start with an injected summary sometimes more reliable than resuming?
→ `shift_monitor/recovery.py::decide` with `STALE_RESUME_THRESHOLD_MINUTES = 30` (~1/16 of an 8-hour shift): empty manifest → `fresh`; complete manifest → `fresh`; last step within 30 min → `resume`, else → `fresh`. Demonstrated live in `fork-recovery-demo.txt`: crash 10 min ago → `resume`; 60 min ago → `fresh`; already-complete → `fresh`. A fresh start is more reliable for stale partials because the working set has moved on — resuming a 60-minute-old partial would continue reasoning from expired intermediate state, while a fresh run re-gathers the current slice and injects whatever findings the manifest already captured as a summary (`test_resumed_prompt_has_both_sections` covers the both-sections resumed prompt shape). The manifest itself is crash-safe JSONL with per-line fsync (`manifest.py::append_step`).

13. **Small state.** Byte size of your `hot_state.json`. Why does the budget matter for a system run once per shift, indefinitely?
→ `state-size.txt`: 980 bytes — a single integer on its own line, measured with `Path('data/hot_state.json').stat().st_size` after the shift-C run (copy at `system-4-orchestrator/hot_state.json`). The budget matters precisely because the system runs forever: hot state is reloaded at the start of every shift, so any growth compounds across hundreds of shifts (unbounded `recent_defect_hashes` alone would eventually dominate the prompt). Capping hashes at 20 (`test_hotstate_rejects_more_than_20_hashes`), writing atomically (`write_atomic`), and keeping the file at 980 bytes « ~5 KB keeps every future shift's fixed overhead negligible while the unbounded history lives in SQLite (`data/warm.sqlite`) and monthly summaries (`cold.py`) instead.

## Part 2 — Synthesis

14. **Three layers.** Point to a file/artifact for each layer and justify.
→ Model: `system-4-orchestrator/recorded-response.json` — the assay content itself (quarantine recommendation for lot 2026-0430-B), i.e. what the model produced; the harness never invents it, only replays it via `RecordedClaudeClient`. Harness: `claims_intake/loop.py::run` (System 1) — the `while True` loop that owns control flow, tool dispatch, budget enforcement, and per-turn tracing around a single model call; the model decides *what* to do next, the harness decides *how* continuation works. Orchestration: `shift_monitor/pipeline.py::run_shift` + `recovery.decide` + `fork.fork_for_hypothesis` (System 4) — multi-invocation coordination across shifts: which slice to load, whether to resume or start fresh, and how parallel hypotheses branch and merge, all outside any single model context.

15. **Deterministic vs prompt.** Cite one behavior guaranteed in code (terminal tool, read-only allowlist, atomic write, byte budget) and one guided by prompt. When is each right?
→ Guaranteed in code: `claims_intake/tools.py::_t_route_to_adjuster` refuses to route unless `classification` and `severity` are already set and `terminal_called` is false — returning a structured `is_error` payload instead of raising — so "exactly one terminal tool per claim, after classification" holds no matter what the model attempts (my demo tripped the field-validation branch of the same function). Guided by prompt: System 1's `SYSTEM_PROMPT` ("look up the policy early … ask one clarifying question per missing piece … commit via classify+assess+terminal") and System 2's `prompts/compression_prompt.md` shape summarization style. Code is right for invariants that must hold under adversarial or confused model behavior (single-terminal, read-only skill allowlists, atomic hot-state writes, the 20-hash cap); prompts are right for judgment calls with no checkable predicate (whether a claim is "genuinely ambiguous," how tersely to phrase a resolved-issue summary).

16. **Context, two faces.** Compare context management in System 2 (intra-session) and System 4 (cross-session) with cited numbers from both. Same principle, different mechanism — how?
→ Same principle: never place retrievable-elsewhere bytes into the model's context. System 2 (intra-session) shrinks one long conversation: baseline 47144 → active-verbatim 19538 + case-facts 149 + small resolved summaries (my deterministic measurements in `offline-measurements.txt`; reference assembly 20,350 / 56.83%). Its mechanism is semantic triage inside the history — prune fields (57→5, 532→45 tokens), summarize resolved threads, preserve the live thread byte-exact. System 4 (cross-session) shrinks state carried *between* shifts: 40-defect SQLite history → 17-row SQL slice in context, 980-byte hot file reloaded next shift (`state-size.txt`, `run-output.txt`). Its mechanism is tiered persistence plus push-down filtering — the model sees a window, never the archive. In short: System 2 reduces what is placed into a model context (one session's prompt); System 4 reduces what state must be carried between sessions (every future session's starting load).

17. **Reliability you can't see in one run.** Name one behavior a test guarantees that a single successful run would not reveal. Why does it matter before shipping?
→ `tests/test_loop.py::test_loop_raises_on_unexpected_stop_reason` (System 1, in the 29-passed suite) guarantees the loop *raises* on stop reasons like `max_tokens` instead of silently returning a truncated claim as complete. My offline 6-turn happy-path trace (`trace-claim_01_kitchen_fire.jsonl`) exercises only `tool_use`/`end_turn` and would pass even with a loop that swallowed `max_tokens` — the first production claim that hit the token ceiling would then be misreported as finished (wrong queue, no escalation, no error row). The AST audits (`test_no_integer_literal_iteration_cap_in_loop`) are the same class: they outlaw a whole family of future edits, not just current behavior. Shipping on green runs alone confuses "worked once" with "fails safely always."

18. **Blast radius.** Pick one system. What's the blast radius if it misbehaves, and what's the kill switch? Ground it in that system's tools, enforcement points, and state.
→ System 1 (claims intake): a misbehaving loop misroutes real claims — wrong adjuster queue (`route_to_adjuster` writes `queues/<queue>.jsonl`), or a wrongful `escalate_to_human` that buries an auto-routable claim in the human backlog; repeated `request_clarification` loops could also spam claimants. Containment is layered in code, not prompts: the `Budget` (`max_input_tokens`, `max_wall_clock_s`) bounds tokens and time per claim; the `terminal_called` short-circuit in `_t_route_to_adjuster`/`_t_escalate_to_human` caps terminal writes at one per claim (`test_double_terminal_is_graceful_error`); handler exceptions become structured `transient` errors instead of crashing the loop; and every turn — including pathological ones — is appended to `traces/<claim>.jsonl` with token counts and `est_cost_usd`, so a runaway claim is visible in `summary.md` and its trace is auditable before queues are consumed downstream.
